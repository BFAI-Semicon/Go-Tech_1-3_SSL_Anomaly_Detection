primary-anomaly-detection 設計サマリ

出典: .kiro/specs/primary-anomaly-detection/design.md（全 1343 行）を要約したもの。判断の根拠と代替案比較は同ディレクトリの research.md にある。

1. この spec の要旨

固定 SSL ViT が出力したパッチ特徴を正常分布と突き合わせ、教師なしで欠陥候補ヒートマップと ROI 候補を得る一次検出を作る。あわせて、特徴抽出からスコア出力までを初めて端から端まで通す VisA 検証ゲート CLI を用意する。

feature_extraction（パッチ特徴抽出）と patch_feature_store（正常メモリバンク）は既に実装済みだが、両者を通す合成ルートが存在しない。本 spec が新規 2 パッケージを積んでパイプラインを接続する。

src/primary_anomaly_detection/

Req 1–6。特徴 → スコア → ヒートマップ → ROI だけを持つ。

データセット・永続化・指標を一切知らない。numpy と scipy のみで書く。

src/visa_gate/

Req 7–10。ロジックを持たず、順序と配線と入出力だけを持つ合成ルート。

CLI を別パッケージにするのは循環依存の回避のため（判断 1）。

3. 4 つの設計判断

判断 1 ｜ 合成ルートを別パッケージにする

CLI を primary_anomaly_detection 内に置くと、パッケージ単位で primary_anomaly_detection → evaluation_framework の import が生まれる。

将来の evaluation_framework → primary_anomaly_detection と相互依存になり、steering が両向きの forbidden contract で禁止している形に触れる。だから visa_gate を切り出す。

判断 2 ｜ Mahalanobis の正常特徴は呼び出し側が供給する

ストアは正常ベクトルの読み出しを公開していない。読み出し API を足すのは patch-feature-store の公開契約変更であり境界外。

VisA ゲートは登録前の正常パッチ特徴を手元に持つので、同じ配列をストア登録と較正の両方へ渡す。この二重利用が唯一の成立経路。

判断 3 ｜ 共通尺度は次元非依存の固定写像

k 近傍は mean(コサイン距離) / 2、Mahalanobis は d / (d + sqrt(D))。どちらも埋め込み次元 D が変わっても同じ規則で [0, 1) に収まる。

画像内 z-score や順位化は採らない。画像ごとに尺度が変わると image-level 比較が壊れるため。

判断 4 ｜ 画素格子は positions から復元する

PatchFeatureSet は画像 H/W を持たないが、max(top) + patch_stride と max(left) + patch_stride が厳密に H/W と一致する。

呼び出し側から H/W を別経路で受け取る形は採らない。特徴と食い違ったときに誤りを検出できなくなるため。

4. 検出フローと分岐

検査順が固定されている理由

順検査この順序でないと起きること
1同一性照合後回しにすると、別のバックボーンで作った分布と突き合わせたスコアが返る。MAHALANOBIS 単独ではストア側の照合が働かない
2形状検査—
3ノルム検査（正規化時）ゼロ除算由来の nan が numpy.quantile まで流れ、しきい値比較が全画素 false になる。ROI 空・エラー無しという「距離だけが無意味」な失敗が表に出ない

同一性不一致とノルム 0 の行が同時に成り立つ入力では、先に通る同一性照合のエラーが出る。この順序自体をテストで固定する。

5. 2 つのスコア方式

観点k 近傍距離（Req 1）Mahalanobis 距離（Req 2）
突き合わせ先正常メモリバンク（search_normal）正常特徴から推定した平均と共分散
入力の供給元ストアが所有呼び出し側が (N, D) 配列で渡す
生の距離コサイン距離 [0, 2] の上位 k 件の平均L z = (x - mu) を三角行列で解いて d = ‖z‖
正規化mean / 2.0 → [0, 1]d / (d + sqrt(D)) → [0, 1)
保持する状態持たない十分統計量（件数・和ベクトル・スキャッタ行列）と Cholesky 因子
不足時のエラーNormalBankTooSmallError（取得件数 < k）NormalFeatureCountInsufficientError（N < D+1 または分解失敗）
フォールバック検知search_normal が空タプルを返すselect() に対応ドメインの較正が無い
記録項目provenance.neighbor_countprovenance.normal_feature_count

較正を十分統計量で持つ意味

  • 平均は sum_vector / sample_count、共分散は (scatter - sample_count · mu muᵀ) / (sample_count - 1) として導出する。元の特徴配列 (N, D) は保持しない。
  • 再較正（Req 2.4）は統計量に追加分を足すだけなので、fit(A).extend(B) と fit(concat(A, B)) が同じ平均・共分散になる。これを不変条件としてテストで固定する。
  • 共分散にリッジ項（eps * I）や縮約は入れない。入れると常に計算できてしまい、Req 2.3 の「不足していることが分かるエラー」が働かなくなる。
  • D = 384 のとき較正 1 件はスキャッタ行列と Cholesky 因子で約 2.4MB。Cholesky は fit / extend の 1 回だけで、scores() では行わない。

融合（Req 3）

融合は重み付き平均 sum(w_i · s_i) / sum(w_i)。各 s_i が [0, 1] なので結果も [0, 1] に収まり、有効方式が 1 つのときは当該方式の正規化スコアそのものになる。方式の走査順は ScoreMethod の宣言順に固定して、浮動小数の加算順まで決定的にする。

運用点は分位点だけで与える。DetectionConfig は異常スコアの絶対値しきい値フィールドを持たない。

6. L2 正規化が起きる 3 箇所

抽出器は埋め込みを L2 正規化しない（timm_backbone.py の正規化は入力画素の平均・分散正規化と backbone final norm だけ）。したがって正規化が起きるのは次の 3 箇所だけで、この 3 つが揃って初めて 3 経路の尺度が一致する。

場所所有対象
patch_feature_store/catalog/admission.pyストア登録ベクトルと問い合わせベクトル
MahalanobisCalibration.fit / extend本 spec較正へ積む正常特徴
PrimaryAnomalyDetector.detect本 specスコア化する入力埋め込み

ここを外すと起きる失敗

  • 較正だけを未正規化空間に残すと、detect() がスコア化する空間（L2 正規化後）と平均・共分散の空間が食い違う。エラーにならずに距離だけが無意味になる。
  • 正規化の定義は scoring/mahalanobis.py の l2_normalize_rows() 1 箇所に置き、engine.py も同じ関数を呼ぶだけにする。2 箇所に書くと、片方だけが退化入力の扱いを変えたときに食い違いが再発する。
  • ノルム 0 の行は ValueError。型と判定はストアの admission と揃える。

7. ヒートマップと ROI

ヒートマップ合成（Req 4）

  • 画素格子は positions から復元する。H = max(top) + patch_stride、W = max(left) + patch_stride。タイル配置が画像全面を被覆し、タイル辺長が patch_stride で割り切れることが上流で保証されているため厳密に一致する。
  • patch_stride の供給元は PatchFeatureSet.identity.patch_stride。H/W と刻み幅を同じ特徴集合から導くので、別経路の値と食い違わない。
  • 各パッチは [top, top + patch_stride) × [left, left + patch_stride) の矩形へ寄与する。
  • 重なり画素は算術平均。寄与スコアの総和と寄与回数を別配列に積んで最後に除算するため、パッチの走査順に依存しない。

最大値ではなく平均を採るのは、タイル境界付近の画素だけが系統的に高くなってタイル格子模様が出るのを避けるため。代わりに、小さな欠陥が重なり領域にあると薄まる（overlap = 0 でも回避できない）。

ROI 切り出し（Req 5）

手順内容
しきい値numpy.quantile(heatmap, roi_quantile)。判定は超過（>）なので、定数ヒートマップでは超過画素が無く空タプルになる
連結成分scipy.ndimage.label を 8 近傍構造（np.ones((3, 3))）で適用
各成分外接矩形を top/left/height/width、成分内最大スコアを representative_score とする
整列と採番代表スコア降順・同点は (top, left) 昇順で整列 → roi_max_count で打ち切り → 先頭から roi_id = 1, 2, ...

整列してから採番するので、同一入力に対して同一の識別子になる。

8. ドメイン別突き合わせ

既定（domain_scoped = false）ではドメインタグを一切参照せず、登録済み正常集合全体を単一プールとして扱う。true にしたときも行うのは「突き合わせ先の分布の選択」だけで、ドメイン不一致を候補除外の理由には使わない（フィルタではない）。

鍵の解決は detect() が _resolve_domain_scope() で 1 回だけ行い、同じ値を 2 方式へ渡す。domain_scoped が false なら None、true なら features.domain をそのまま返し、軸の欠けを補完も除去もしない。方式ごとに別の解決を行う経路は作らない。

2 方式の引き当て範囲は非対称。これを許容する

k 近傍側はストアの DomainCriteria に写して引くが、ストアは空集合の軸を「無指定（何にでも一致）」として扱う。一方 Mahalanobis 側は by_domain の辞書キー完全一致。同じ鍵でも k 近傍の候補集合のほうが広くなり得る。

較正側に軸ごとの緩和を実装しないのは、鍵ごとに独立した平均・共分散を持つ較正から「軸を緩めた集合の分布」を合成する手段が無いため。十分統計量を足せるのは同じ母集団の追加分だけで、異なる母集団の合算は fit(A).extend(B) == fit(concat(A, B)) の意味を崩す。

両方式は該当有無を独立に判定し、片方だけ該当ありでもエラーにしない。それぞれが自分の経路でプールへ落ちる。

項目k 近傍側Mahalanobis 側
検知点ドメイン指定の search_normal が空タプルを返すMahalanobisCalibrationSet.select() に対応較正が無い
動作同じクエリを domain=None で組み直して再探索プール較正へ切り替え
伝達口neighbor_distances() の 2 要素目select() の 2 要素目

件数不足の判定はフォールバック後の距離列に対して行う。そのため「ドメイン指定で 0 件」がバンク件数不足として誤検知されることはない。detect() は有効な方式の分だけ論理和を取り、結果に 1 つの domain_fallback_applied として集約する。

記録は 2 フィールドに分ける

フィールド意味domain_scoped = false
domain_scope要求した鍵。フォールバックしても None へ書き換えないNone
domain_fallback_appliedいずれかの方式が実際にプールへ落ちたかfalse

1 つのフィールドに「要求」と「結果」を持たせると、None が「ドメイン限定していない」と「限定したが落ちた」の両方を意味してしまう。分ければどちらの状態も曖昧さなく復元できます。なお、どちらの方式が落ちたかは記録しません（Req 6.4 が求めていないため）。

9. VisA 検証ゲート

実行順序

  1. 実行前検証と root の解決 — data_root の存在 → カテゴリの準備状態 → 未準備かつ未許可ならエラー → 準備するなら書き込み可否。visa_image_source() は内部で prepare_data() を呼び、未取得なら確認なしに約 16GB のダウンロードを始めるため、検証を後段に置けない。resolve_prepared_visa_root() は判定と同時に「anomalib へ渡す root」を返し、guard の判定と抽出の入力が食い違わないようにする。
    準備済みと認める配置は 3 つ： data_root/visa_pytorch/{category} と data_root/{category} は data_root を返し、配布元の前処理済みレイアウト data_root/VisA_pytorch/1cls/{category} は data_root/VisA_pytorch/1cls を返す（anomalib はこれを 2 つ目の経路として認識する）。
  2. 実行ディレクトリの採番 — {category}__{backbone}、既存なら -2, -3, ... の未使用最小連番。時刻を使わないので決定的で、既存結果を上書きしない。
  3. train/good の抽出 — 画像ソースと抽出エンジンを組み立ててパッチ特徴を得る。
  4. 二重利用 — 同じ抽出結果を (a) 既知正常としてストアへ一括登録、(b) Mahalanobis 較正の入力として渡す。どちらもそのまま渡す（L2 正規化は受け手が各々行う）。
  5. coreset 再選抜 → 保存 → 復元 — reselect_coreset(round(coreset_rate × 登録パッチ数)) の後 save() し、restore() で読み直す。永続化されたバンクでスコア化することが Req 7.1 の要求。
  6. 検出器の構築 — normal_identity には登録と較正に使った train/good の identity を渡す。ストアは自身の同一性メタを公開しないため、正常分布を生成した抽出器を知っているのはこの合成ルートだけ。
  7. test 分割の各画像 — 抽出 → 検出 → スコアマップと ROI を保存。
  8. 指標 — image-level スコアはゲート側で heatmap.max() として求め、port へ渡す。image_level_auroc < 0.9 なら below_provisional_floor を true にする（警告であって失敗ではない）。

タイル設定を共通定数ではなくプリセットに持たせるのは、FeatureExtractionEngine が tile_size % patch_stride == 0 を構築時に要求する一方、DINOv2 の timm 実装だけ patch 14 で 512 % 14 != 0 になるため。共通の 512 だと --backbone dinov2 が必ず ValueError で落ち、逆に全体を 518 に寄せると patch 16 系が落ちます。518 = 14 × 37、wide_resnet50_2 の layer3 は reduction 16 です。

その結果 dinov2 だけタイルサイズが揃いませんが、パッチストライドが 14 と 16 で異なる時点でパッチグリッドは揃わず、ゲート文書も「バンクサイズはパッチ数でも揃える」として差の存在を前提にしています。実値は run_conditions.json に残ります。

ゲート既定の GATE_DETECTION_CONFIG は k 近傍と Mahalanobis を等重み 1.0 で両方有効にする。ゲートの目的は 2 方式と融合経路の配線確認であり、片方だけでは検証できない経路が残るため。

10. 公開 API

公開する面と公開しない面

規則は既存 3 パッケージと同じで、engine をルートに出し、公開シグネチャに現れる型はすべて公開する。

区分シンボル
enginePrimaryAnomalyDetector
設定DetectionConfig, ScoreMethod
結果PrimaryDetection, RoiCandidate, ScoringProvenance
較正MahalanobisCalibration, MahalanobisCalibrationSet
port と入口NormalNeighborSearch, store_normal_neighbor_search
例外PrimaryDetectionError, NormalBankTooSmallError, NormalFeatureCountInsufficientError, NormalReferenceIdentityMismatchError
公開しないknn_scores, fuse_scores, compose_heatmap, extract_roi_candidates, l2_normalize_rows

較正型を公開するのは PrimaryAnomalyDetector.__init__ の引数型であり、かつ較正の生成（fit）を行うのが合成ルートだから。出さないと visa_gate が primary_anomaly_detection.scoring.mahalanobis を直接 import することになり、中間層のモジュールがパッケージ間契約になってしまいます。

逆にスコア関数群を公開しないのは、いずれも detect() が定めた順序（同一性照合 → 正規化 → スコア → 融合 → 合成 → ROI）の内側の手順であり、個別に呼べるようにすると検査順を迂回した経路ができるためです。

visa_gate 側は run_visa_gate・VisaGateConfig・VISA_CATEGORIES・GATE_BACKBONE_PRESETS・GateRunSummary・GateRunConditions・GateMetricValues・GateMetrics・VisaGateError とその派生を公開します。

    domain_scope: DomainTags | None       # 要求した鍵。フォールバックしても書き換えない
    domain_fallback_applied: bool         # いずれかの方式がプールへ落ちたか
    identity: ExtractorIdentity


@dataclass(frozen=True)
class PrimaryDetection:
    patch_scores: np.ndarray             # (P,) float32。入力行と 1 対 1
    heatmap: np.ndarray                  # (H, W) float32
    roi_candidates: tuple[RoiCandidate, ...]
    provenance: ScoringProvenance

patch_scores の行は入力 PatchFeatureSet.embeddings の行と 1 対 1 なので、パッチ位置を再掲するフィールドは持たない（呼び出し側が特徴集合を保持している）。

11. エラーの分類

すべて例外で表現し、パッケージごとに単一の基底例外（PrimaryDetectionError / VisaGateError）を置く。エラーは原因を特定できる属性を持ち、メッセージ文字列の解析を強いない。

型分類送出点Req
ValidationError設定pydantic の構築時検証（空の方式集合・範囲外の分位点・非正の k）3.7
NormalBankTooSmallError入力不足フォールバック後の取得件数が k 未満1.3
NormalFeatureCountInsufficientError入力不足N < D+1 または Cholesky 失敗2.3
NormalReferenceIdentityMismatchError同一性detect() 冒頭。入力の同一性メタ vs 申告された正常参照9.5
ExtractorIdentityMismatchError同一性ストア。問い合わせの同一性メタ vs ストアが保持する値（patch_feature_store が所有）9.5
ValueError退化入力l2_normalize_rows()。ノルム 0 の行。基底例外の対象外—
DatasetRootMissingError実行前検証データルート不在9.1
DatasetNotPreparedError実行前検証未取得かつ --download 未指定9.3
DatasetLocationNotWritableError実行前検証準備が必要だが書き込み不可9.4

同一性の判定点が 2 つある理由

検出器は「入力特徴の同一性メタ」と「申告された正常参照の同一性メタ」を照合する。ストアは「問い合わせの同一性メタ」と「自身が保持する同一性メタ」を照合する。後者は、normal_identity の申告自体がストアの実体とずれている場合を捕まえる別の事実に対する検査であり、どちらもそのまま伝播させてスコアを 1 件も出さない。

前提条件違反（形状・有限値・L2 ノルム 0）はストアの admission と同じく ValueError で弾き、基底例外の対象外とする。同じ事実に境界ごとに別の型を投げると呼び出し側が両方を捕捉する羽目になるため。CLI もこの ValueError は捕捉せず伝播させる（組み込み型を広く捕捉すると無関係な実装バグまで 1 行メッセージに畳まれ traceback が失われる）。フォールバックと ROI 該当なしはエラーではない。

14. import-linter 契約

  • primary_anomaly_detection 層順: engine → boundary | scoring | localization → model
  • model 内層順: ports | results → config → errors | types
  • scoring/* 相互と localization/* 相互、visa_gate/boundary/* 相互の independence
  • torch / timm / anomalib / faiss を primary_anomaly_detection 全体で forbidden（allow_indirect_imports = true 付き）
  • patch_feature_store を model / scoring / localization / engine から forbidden — ストア型に触れられるのは boundary だけであることを CI で強制
  • primary_anomaly_detection から visa_gate / evaluation_framework / correction_layer を forbidden
  • correction_layer / feature_extraction / patch_feature_store から新規 2 パッケージを forbidden
  • visa_gate 層順: cli → gate → boundary → model
allow_indirect_imports = true を付ける理由
既定は false で間接チェーンも違反になる。boundary/store_neighbors.py は patch_feature_store を使い、その公開 root は boundary/faiss_index.py を import するため、既定のままでは「ストアの公開 API を呼ぶだけ」の実装が faiss 違反として落ちる。true にすると直接 import だけが違反になり、「どの層も ML ライブラリを直接 import しない」という宣言を boundary まで含めて検査できる。既存 2 パッケージのように source_modules から boundary を除く形は採らない（本パッケージの boundary は ML ライブラリを必要とせず、検査対象から外す理由がない）。
visa_gate に ML ライブラリ contract を置かない理由
合成ルートとして faiss_flat_index / anomalib_coreset_selector / visa_image_source など boundary 由来の公開ファクトリを直接呼ぶ必要があるため。ML ライブラリ隔離は各ドメインパッケージ側で担保する。
後回しにする契約が 1 つある
evaluation_framework → visa_gate の逆向き禁止は、同パッケージが未実装で root_packages に加えられないため、evaluation-framework 実装時に追加する。

15. テスト計画

単体 26 統合 14 E2E 1

とくに意図が強いテスト

  • fit(A).extend(B) と fit(concat(A, B)) が同じ距離を返す — 再較正の定義そのものを固定する。
  • 未正規化の normal_features で fit しても、行ごとに L2 正規化した配列と同じ平均・共分散・距離になる（かつ冪等）— 抽出器が L2 正規化しない事実に対する回帰テスト。
  • ドメイン指定で 0 件・プールで k 件を返す偽 port に対して、NormalBankTooSmallError を送出せず 2 要素目を true にする — フォールバック前の 0 件を件数不足と誤判定しないことと、伝達口が戻り値にあることを同時に固定。
  • MAHALANOBIS 単独構成でノルム 0 の行を含む入力が ValueError になる — ストア側の検査が働かない構成でも、退化入力が nan として分位点まで流れないことを固定。空の ROI 一覧が定数ヒートマップの場合だけに限られることも併せて示す。
  • 同一性不一致とノルム 0 の行を同時に持つ入力が NormalReferenceIdentityMismatchError になる — 検査順を固定する。
  • compose_heatmap がパッチ入力順を入れ替えても同一結果 — 重なり配置には overlap = 0 かつ画像サイズが tile_size の倍数でない端寄せ配置を含める。
  • 偽 GateMetrics が 0.85 / 0.95 を返す構成で below_provisional_floor が切り替わる — 実データ・実重み・指標実装のいずれにも依存しない決定的テストとして置く。
  • k 近傍は該当あり・Mahalanobis は鍵なしの構成で、domain_scope が要求値のまま domain_fallback_applied が true になる — 2 方式の引き当てが非対称でもエラーにならず、記録の 2 フィールドが「要求」と「落ち先」を別々に表すことを固定。
  • VISA_CATEGORIES が anomalib の CATEGORIES と一致する（pytest.importorskip 付き） — 写した定数が上流の実測値からずれたときに落ちる回帰点を 1 箇所に集める。
  • resolve_prepared_visa_root が 1cls 配置で data_root/VisA_pytorch/1cls を返す — guard が準備済みと認めた配置と抽出へ渡す root が食い違わないことを固定。
  • 各プリセットで実重みの patch_stride が tile_size を割り切り、抽出エンジンが構築できる（重み未取得なら skip） — dinov2 の patch 14 と 518 の組み合わせが実際に通ることの確認。
  • 公開面が 12 シンボルと一致し、スコア関数群を公開しない — visa_gate が中間層モジュールを直接 import しない前提を固定。

E2E は 3 条件が揃うときだけ実行

VisA データが取得済み（resolve_prepared_visa_root がエラーを出さない）、バックボーン重みが取得可能（BackboneUnavailableError → skip の踏襲）、evaluation_framework が import 可能（pytest.importorskip）。欠けていれば pytest.skip する。実行時は暫定下限の判定を実測値に依存させず、AUROC は成果物として残すだけにする。

16. 性能とリスク

項目内容
近傍探索の回数search_normal は 1 クエリ 1 呼び出しで、バッチ探索の公開経路が無い。コストは「テスト画像数 × 画像あたりパッチ数」に比例する。ドメイン指定でフォールバックする構成では 1 パッチにつき最大 2 回（ゲート既定は 1 回に固定）
登録コストregister() は登録のたびに既存プロトタイプ全体への最近傍探索を行い、train/good の画像数 × パッチ数に対して二次的に効く。merge_distance_threshold = 0.0 は完全一致だけを集約する設定で、登録件数を減らさない
共分散D = 384 で (D, D) float64 は約 1.2MB。較正 1 件で約 2.4MB。十分統計量方式なので正常特徴の配列を保持し続ける必要がない

未充足の依存とリスク

  • evaluation_framework の image-level AUROC / AUPRO は現時点で未実装。port と GateMetricValues は本 spec が所有し、アダプタが詰め替える形にして待ちを切り離している。
  • 近傍探索がパッチごとの逐次呼び出しになるため、実データ投入時の主要ボトルネック候補。バッチ探索が必要になった場合は patch-feature-store 側の契約追加として扱う。
  • 較正対象はストアの現在の生存集合ではなく呼び出し側が渡した集合。coreset 再選抜や剪定の影響は較正に反映されない（ゲートでは登録直後の全件を渡すため実害なし）。
