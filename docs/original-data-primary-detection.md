# オリジナルデータでの一次検出：必要なものと測れるもの

spec 2–4（抽出・ストア・一次検出）が揃った時点で、独自の半導体検査画像を通すために
**新たに作るもの**と、それが揃ったときに**測れるもの**を固定する。

対象は **正常のみで、欠陥ラベルも画素マスクも無い** 実機画像である。
AUROC / AUPRO / 流出率は算出せず、主張しない。
測り方の詳細は [normal-only-validation-plan.md](./normal-only-validation-plan.md)、
VisA 側の公式ゲートは [visa-validation-gate.md](./visa-validation-gate.md) を参照する。

## 現状で足りているもの

次は実装済みであり、オリジナルデータ用に作り直さない。

| 部品 | 所在 | オリジナルデータで使う内容 |
| --- | --- | --- |
| パッチ特徴抽出 | `feature_extraction` | タイル化、ViT/CNN、抽出器同一性 |
| フォルダ入力 | `folder_image_source()` | ディレクトリ指定で画像を読む。VisA 配置は不要 |
| ドメイン／出自の添付口 | `ImageMetadata` | `DomainTags` と `ProvenanceKeys` を `metadata_index` で渡せる |
| 正常メモリバンク | `patch_feature_store` | 登録、近傍探索、coreset、スナップショット |
| 一次検出 | `primary_anomaly_detection` | k 近傍／Mahalanobis、ヒートマップ、ROI |

`visa_gate` は使わない。カテゴリ定数・3 配置の guard・`visa_image_source()` が
VisA 専用であり、`--data-root` に独自画像を置いても通らない。

## 作る必要があるもの

段階は 2 つに分ける。A が無いと一次検出は起動できない。
B 以降は「数値としての検証」に進むための追加である。

### A. オリジナルデータ用の合成ルート（動作確認の前提）

抽出・ストア・検出を VisA 以外の入力でつなぐ composition root。
既存 API を呼ぶだけで、検出ロジックは新規に書かない。

含めるもの:

- 画像ルートと分割（バンク用正常／評価用正常）を `folder_image_source()` に渡す組み立て
- バックボーンは `GATE_BACKBONE_PRESETS` を再利用してよい（タイルサイズと
  `patch_stride` の整合が既に閉じている）
- `train` 相当の正常をストアへ登録し、同じ配列で Mahalanobis を較正する
  （ストアは正常ベクトルの読み出しを公開しない）
- 評価画像ごとに `detect()` し、スコアマップと ROI を保存する
- 起動口（`scripts/` ＋ `mise` タスク）。`visa_gate` には足さない

これが無いと、公式 CLI もテスト以外の経路もオリジナルデータを読めない。

### B. 画像単位の閾値（過検出率の前提）

`detect()` は連続スコアと画像内 ROI だけを返す。画像を「フラグする／しない」は持たない。
過検出率を出すには、画像スコア（現状は `heatmap.max()`）に閾値を当てる層が要る。

閾値は**評価集合の上位 q%** から決めてはならない。定義上、過検出率が q になり情報が消える。
バンクにも評価にも入れない較正用サブセットの分位点から決め、評価集合に適用する
（[normal-only-validation-plan.md](./normal-only-validation-plan.md) §2）。

この層の所有は `evaluation-framework` である。一次検出パッケージには足さない。

### C. 正常のみ検証の実験プロトコル（安定性・シフトの前提）

`evaluation-framework` が所有する集計と分割。指標計算はスコア列だけを受け、
検出実装に依存しない。

| プロトコル | 必要な入力 | 出すもの |
| --- | --- | --- |
| 3 役分離 | バンク／較正／評価の互いに素な分割 | 閾値と過検出率 |
| 複数バンク＋共通評価 | 評価画像を、それを含まない複数バンクでスコア化 | フラグ頻度、Jaccard、κ、Spearman |
| ドメイン別グループ分割 | 装置・工程などが付いた評価集合 | S1 との過検出率差（シフト影響量） |
| グループキー分割 | ウェハ ID／ロット ID／撮像日 | 近重複リークを除いた分割 |

A だけでは 1 バンク・1 回の `detect()` しか回せず、安定性とシフト量は定義できない。

### D. データ側のメタデータ（プロトコル C の入力）

コードではなく、オリジナルデータが持つ情報。抽出器は受け口だけを持つ。

| フィールド | 型 | 無いときに失うもの |
| --- | --- | --- |
| `DomainTags`（工程・材料・装置） | `ImageMetadata.domain` | ドメイン別分割（S2）。シフト影響量が測れない |
| `ProvenanceKeys`（ウェハ・ロット・撮像日） | `ImageMetadata.provenance` | グループキー分割。近重複リークで過検出率が楽観的になる |

メタデータが一切無い場合でも A は動く。測れるのは動作確認と、ランダム分割の過検出率までである。

## 揃ったときに測れるもの

| 揃っているもの | 測れる／確認できる | 測れない |
| --- | --- | --- |
| spec 2–4 のみ | なし（オリジナル入力の起動口が無い） | すべて |
| ＋ A | 一次検出の動作確認。1 枚ごとのスコア・ヒートマップ・ROI | 過検出率、安定性、シフト影響量 |
| ＋ A と B、較正／評価の分割 | 1 バンクに対する過検出率（画像単位・パッチ単位） | 安定性、シフト影響量 |
| ＋ A〜C、ドメイン無し | 過検出率と安定性（ランダム分割＝ノイズ床） | シフト影響量 |
| ＋ A〜D | 過検出率、安定性、ドメインシフト影響量、汚染候補の洗い出し | AUROC / AUPRO / 流出率、検出力の優劣 |

汚染候補は、フラグ頻度が高い画像をリストに出すところまでが自動側である。
目視分類の実施は `llm-feedback-structuring` の先であり、本メモの範囲外とする。

## 主張しないこと

次はオリジナル正常データでは原理的に出せない。評価基盤を実装しても変わらない。

- image-level AUROC、AUPRO、PG2、F1-Max、AUPRC
- 流出率（escape rate）・見逃し
- 特徴抽出モデルの検出力の優劣（VisA / MIIC で測る）
- 単一ドメイン内の過検出率によるモデル比較（較正分位点で値が決まり自明化する）
- 「安定している＝検出器として良い」

## spec との対応

| 作るもの | 所有者 | 実行順 |
| --- | --- | --- |
| A 合成ルート | 未所属。`visa_gate` に足さない。新規 composition root | 4 の後、6 の前でも着手可 |
| B 画像単位閾値 | `evaluation-framework` | 6 |
| C 分割と集計プロトコル | `evaluation-framework` | 6 |
| D メタデータ | データ準備（コード外）。受け口は spec 2 済み | データ用意の時点 |

順序 6 の前倒し（VisA ゲート用 AUROC / AUPRO）だけでは A〜C は埋まらない。
オリジナルデータの数値検証は、同 spec 本体の正常のみプロトコルとして扱う。
