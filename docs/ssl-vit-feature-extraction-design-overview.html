ssl-vit-feature-extraction 設計サマリ

出典: .kiro/specs/ssl-vit-feature-extraction/design.md（949 行）／新設パッケージ src/feature_extraction。この HTML は要約であり、正典は design.md。

1. この spec の要旨

検査画像を取り込み、タイル化・パッチ化し、重み固定の自己教師あり事前学習済み ViT でパッチ特徴を生成する、パイプラインの起点パッケージ feature_extraction を新設する。生成物は「1 画像 = 1 PatchFeatureSet」で、各パッチには元画像内の位置が、画像単位ではドメインタグ・由来キー・抽出器同一性メタ・抽出条件が付随する。

利用者は下流 spec の合成ルート（patch-feature-store、primary-anomaly-detection、evaluation-framework）であり、これらは本機能が定義する型だけを介して特徴を受け取り、anomalib・timm・torch の型に依存しない。既存 correction_layer と同じ層パターン（model → geometry / boundary → engine）を踏襲した 2 つ目のパッケージになる。

Goals

  • データセット入力（画像・split・画像単位ラベル・正解マスク）を本機能の型へ閉じ込め、anomalib の型を下流へ漏らさない。
  • 超高解像度画像を、領域欠落なく、暗黙のリサイズなしにタイル化し、1 枚あたり数千〜数万パッチの特徴を生成する。
  • バックボーンを設定値の変更だけで切り替え、前処理条件を全バックボーンに同一の解釈で適用する。
  • 各パッチに元画像座標の位置を、画像単位にドメインタグ・由来キーを付与する。
  • 抽出器同一性メタ（バックボーン名・重みリビジョン・前処理条件・埋め込み次元）と抽出条件（パッチ数・タイル化条件）を出力する。

Non-Goals

  • 異常スコア計算・ヒートマップ・ROI 抽出、特徴の永続化・索引・近傍検索・coreset、評価指標の算出。
  • バックボーンの重み更新、ローカルでの自己教師あり事前学習、MAE 再構成経路。
  • 複数層特徴の融合・マルチスケール抽出（1 回の抽出は単一層に閉じる）。
  • ドメインタグの生成・正規化・外部システムとの突合（値は入力から供給される）。

3. 3 つの設計判断

① Protocol 注入

engine は具体実装を型として知らず、InspectionImageSource と PatchFeatureExtractor の 2 つの Protocol だけを受け取る。合成ルートを組むのは下流 spec の呼び出し側であり、どの入力元・どのバックボーンを使うかの選択も呼び出し側が行う。

② 設定は境界で解決する

タイル化条件・前処理条件・バックボーン指定は境界で解決し、内部には解決済みの値だけを流す。解決は構築前に 1 度だけ行い、「構築に適用した値と記録する値が一致する」不変条件を保つ。

③ バックボーン差は boundary で吸収

ViT のトークン列（output_fmt="NLC"）と CNN の特徴マップ（"NCHW"）の差は boundary 内で (タイル数, パッチ数, 次元) へ正規化し、geometry と engine は「パッチストライド」という単一の概念だけを扱う。

engine の契約

class FeatureExtractionEngine:
    def __init__(self, extractor: PatchFeatureExtractor, tiling: TilingConfig) -> None: ...
    def extract_image(self, image: InspectionImage) -> PatchFeatureSet: ...
    def extract_split(
        self, source: InspectionImageSource, split: DatasetSplit
    ) -> Iterator[PatchFeatureSet]: ...
  • 事前条件: tiling.tile_size % extractor.identity.patch_stride == 0（構築時に検証し、違反は ValueError）。image.pixels は (3, H, W) float32 で H >= tile_size かつ W >= tile_size。
  • 事後条件: embeddings.shape == (P, identity.embedding_dim)、positions.shape == (P, 2)、conditions.patch_count == P。positions の各行は元画像の範囲内。
  • 不変条件: embeddings と positions の行順が一致する（タイル順・タイル内行優先）。
  • extract_split は遅延評価の generator。生成順と件数は source.images(split) と同一で、並べ替え・重複排除・フィルタを行わない。1 枚分が数百 MB になりうるため全画像分を同時に保持しない。
  • extract_split の失敗は変換せず即座に伝播し、以降の画像へ進まない。失敗を集約する経路も、飛ばして続行する経路も持たない。すでに yield 済みの結果は呼び出し側に残る。split が空の場合の DatasetInputError は extract_split の呼び出し時点で表面化する。

6. データモデル

集約の単位は「1 画像」。InspectionImage が入力側の集約ルート、PatchFeatureSet が出力側の集約ルートであり、由来キー・ドメインタグ・同一性メタ・抽出条件はすべて画像単位で 1 つだけ存在する。パッチは独立した実体を持たず配列の行として内包されるため、「同一画像由来の全パッチが同一の由来キーを共有する」不変条件が型で保証される。

設定型：同一性と実行条件を分ける

型持つもの役割
BackboneConfigname, feature_layer, feature_layout, weights_revision「どの抽出器か」。この 4 項目が同じなら同じ抽出器であり、ExtractorIdentity の権威になる

同一バックボーンをデバイス違い・バッチ違いで走らせる構成でも BackboneConfig は 1 つで足り、要件 4.1 の「設定の変更だけで切り替える」が実行条件の再指定を伴わない。分割方式の設定型は持たない（anomalib の ValSplitMode / TestSplitMode は boundary が固定値で渡すだけ）。

BackboneConfig の _check_layer_matches_layout は TOKENS のとき feature_layer が blocks.<int> 形式であることだけを検証する。FEATURE_MAP の層名に形式制約を課さないのは、CNN の層名が timm のモデル系列ごとに異なり blocks.<stack_idx> も正当な登録名になるためで、正しい条件は「対象バックボーンの層一覧に実在するか」＝ライブラリを構築しないと判定できない条件であり boundary が担う。

8. 要件との対応

要件基準主要な実現手段
1. データセット入力の取得と型の閉じ込め6AnomalibDatasetSource.images(split) が InspectionImage を返す。split は固定値指定で本機能が確定させ、マスクは gt_mask の有無だけで決める。失敗は DatasetInputError(location, reason)
2. 超高解像度画像のタイル化・パッチ化5plan_tiles の原点クランプでパディングなしに全域被覆。TilingConfig のバリデータが不正値を拒否。固定バッチで全タイルを走査し打ち切り分岐を持たない
3. 重み固定バックボーンによる特徴生成5ロード時に全パラメータの requires_grad を落とし eval() + inference_mode()。固定バッチ形状（端数は 0.0 充填）で同一デバイス上の再現性を担保
4. バックボーン切替と前処理条件の統一4BackboneConfig の変更だけで切替。未指定条件は pretrained_cfg から解決し ResolvedPreprocessing に記録。適用できない組み合わせは構築前に拒否
5. 位置・ドメインタグ・由来キーの付与5patch_positions が元画像座標を全パッチ分生成。タグ・キーは画像単位で保持し、未供給は None のまま補完しない
6. 抽出器同一性メタと条件の出力4ExtractorIdentity と ExtractionConditions を PatchFeatureSet が同一オブジェクトで保持。リビジョン解決不可は weight_revision = None

9. エラーの分類

失敗は早期に、原因の対象と理由を伴って送出する。握りつぶしと既定値へのフォールバックを行わない。例外クラスは構造化された情報が必要な 2 箇所だけに定義し、それ以外は ValueError を使う。

分類送出する型代表条件判定時点
設定エラー pydantic の検証エラー / ValueError tile_size <= 0、overlap の範囲外、TOKENS × layer3、tile_size % patch_stride != 0、FEATURE_MAP × BACKBONE_FINAL_NORM の明示指定、vit を含む名前 × FEATURE_MAP、解釈できない device、画像寸法 < tile_size すべてモデル構築前
入力エラー DatasetInputError(location, reason) ルート不在・読み取り不可・prepare_data() / setup() がデータを用意できない・指定 split が空・image_path が None ファクトリ呼び出し時（split が空は images(split) 呼び出し時）
バックボーンエラー BackboneUnavailableError(backbone_name, reason) 未登録 arch 名・不正タグ・feature_layer 不在（構築前検証）／重み取得失敗の OSError・RuntimeError（構築呼び出し） 抽出開始前（extract を 1 度も呼ばない）
メタ取得の縮退 例外を送出しない 重みリビジョンを解決できない → weight_revision = None で出力を継続 唯一の縮退経路

設定の組み合わせ不整合を BackboneUnavailableError に入れない。この例外は「重みが取得できない」「バックボーン名が利用できない」ための報告契約である。

10. 実測から決まった規則

design.md の分量の大半は「ライブラリの既定に委ねると契約が壊れる」箇所の固定である。各行を開くと根拠が読める。

anomalib に分割を作らせない

Folder の既定は val_split_mode=FROM_TEST ＋ val_split_ratio=0.5 で、test_data を random_split の戻り値で再代入する（Visa は SAME_AS_TEST で VAL を TEST と同一集合にする）。さらに seed=None では torch.randperm をグローバル RNG で回すため分割が実行ごとに変わる。

そこで両ファクトリは val_split_mode=ValSplitMode.NONE と test_split_mode=TestSplitMode.FROM_DIR を固定値で渡し、分割方式を設定として受け取らない。DatasetSplit は TRAIN / TEST の 2 つだけで、VAL メンバーを置かない（ValSplitMode.NONE では val_data 属性自体が作られず、常に DatasetInputError になる引数値を型に残さない）。folder_image_source は normal_test_dir を必須にする（無いと TRAIN から TEST へ正常画像がサンプリングされる。実測で TRAIN 6→5 件、TEST 4→5 件になり、移った画像は実行ごとに異なった）。結果として RNG を使う経路が 1 つも残らず、seed を設定項目として持つ必要がない。

マスクは gt_mask の有無だけで決める

anomalib は task を「mask_path が全件空かどうか」で推論し、SEGMENTATION のとき正常サンプルへ全ゼロマスクを合成する。したがって同じ正常画像が、mask_dir あり構成では全ゼロの実マスク、なし構成では None になる。

本設計は gt_mask is None のときだけ ground_truth_mask = None とし、それ以外は非ゼロを True とする (H, W) bool を返す。合成ゼロマスクを None へ丸めない。丸めると下流が「マスク未提供」と「異常画素ゼロ」を区別できなくなる。よって ground_truth_mask is None は「データセット構成が画素単位マスクを持たない」ことを表し、画像単位では揺れない。

重み取得失敗を捕捉する位置は 1 箇所だけ

timm.get_pretrained_cfg(name, allow_unregistered=False) はレジストリの辞書引きだけを行い、ネットワークにも重みファイルにも触れない。ここが拒否するのは未登録 arch 名と不正タグ（要件 4.4）である。既定の allow_unregistered=True では未登録 arch に None が返り、以降の .to_dict() が AttributeError になるため False を渡して失敗経路を 1 つにする。

実際の重み取得は TimmFeatureExtractor の構築内側の timm.create_model(pretrained=True) で起きる。この 1 呼び出しだけを try で囲み、OSError（Hugging Face hub 由来の失敗はすべてこれを継承する。LocalEntryNotFoundError → FileNotFoundError → OSError 等を MRO で確認済み）と RuntimeError（timm の重み不在・パス不正・state_dict 不一致）を BackboneUnavailableError へ変換し、raise ... from exc で原因を保つ。それ以外の例外型は素通しにして実装の誤りを隠さない。

端数バッチは 0.0 で充填して形状を固定する

数値が再現するのは同一バッチ形状のときだけなので、末尾の端数は runtime.tile_batch_size まで詰めて推論し余剰行を破棄する。eval() 実行では標本間で統計が混ざらない（BatchNorm は running statistics を使い、LayerNorm はトークン内で閉じる）ため充填値は保持行に影響しない。CPU 上の小規模モデルで実 5 枚 + 充填 3 枚の充填内容を 0 と乱数に入れ替えても、保持 5 行がビット単位で一致した。

再現性の保証は同一デバイス・同一 tile_batch_size に限る。CPU と CUDA では最大差 1.45e-4 で、CUDA の GEMM はリダクション順序がバッチ内要素数に依存するため決定性 API を全て立てても解消しない。

weight_revision はキャッシュ照会だけで解決する

解決順序は 明示指定 → Hugging Face キャッシュの commit → None で、ネットワークアクセスを前提にしない。try_to_load_from_cache に model.safetensors → pytorch_model.bin の順で照会し、str が返った候補のパス <cache>/snapshots/<commit>/<候補> の親ディレクトリ名を commit として採る。

戻り値は「パス」「非存在がキャッシュ済みであることを表すセンチネル _CACHED_NO_EXIST」「未キャッシュの None」の 3 値。センチネルは真値でありパスとして扱うと不正な commit を記録するため、判定は isinstance(result, str) で行う。config.json は照会しない（timm 登録名での構築では重みファイルしかキャッシュに現れない）。custom_load が真のタグは重みが HF キャッシュに現れないため None へ縮退するが、専用の分岐は設けない。

vit を含む名前 × FEATURE_MAP は設定エラーとして拒否する

TimmFeatureExtractor の経路選択は output_fmt == "NLC" または バックボーン名に vit を含むかで決まるため、この組み合わせはライブラリ上は成立する（実測で vit_small_patch16_dinov3 × blocks.5 × NCHW が構築・forward とも成功し (2, 384, 4, 4) を返した）。

しかし FEATURE_MAP のパッチストライドは reductions から採る規則で、この属性は features_only 経路にしか設定されない。したがって構築前に ValueError で拒否し、BackboneUnavailableError には入れない。feature_layer の実在検証も timm_patch_extractor が行う（anomalib は CNN 経路で見つからない層を警告ログのみで layers から取り除き、ViT 経路では範囲外のブロック番号が最初の forward まで遅延するため、構築成功として扱わない）。

patch_stride の権威は ExtractorIdentity だけ

port に専用の問い合わせ口を置かず、engine は extractor.identity.patch_stride を読む。positions は (top, left) の 2 列に留め、パッチ辺長を全 P 行に複製しない（権威データから一意に復元できる値の重複保持になるため）。下流は 1 パッチの領域を (top, left) と identity.patch_stride から復元する。

ExtractorIdentity は feature_layout も持つ。落とすと blocks.<int> が両レイアウトで正当な層名になりうる構成（EfficientNet 系）で、レイアウト違いの 2 つの抽出器が出力上区別できなくなる。パッチストライドは ViT 系で公開属性 patch_size、CNN 系で reductions の該当層の値を採り、内部の feature_info へ直接到達しない。

前処理条件の解決と拒否は resolve_preprocessing の 1 箇所に置く

未指定の input_mean / input_std は pretrained_cfg から、未指定の feature_normalization は feature_layout から決める（TOKENS → BACKBONE_FINAL_NORM、FEATURE_MAP → NONE）。同じ関数が FEATURE_MAP × BACKBONE_FINAL_NORM の明示指定を ValueError で拒否する。既定を決める規則と適用できない指定を拒否する規則は「features_only 経路では norm が効かない」という同一の事実の裏表なので、2 つのモジュールに分けない。timm_patch_extractor はこの例外を捕捉も変換もせず素通しにする。

resolve_preprocessing は embedding_dim を必要としない。feature_normalization が TimmFeatureExtractor の norm 引数に対応する以上、解決は構築より前に完了していなければならず、構築後にしか得られない embedding_dim と同じ関数に置くと既定規則が二重化するか、適用値と記録値が食い違う。

11. import-linter 契約

pyproject.toml の [tool.importlinter] は root_package = "correction_layer"（単数形）であり、新規パッケージは検査対象外になる。root_packages = ["correction_layer", "feature_extraction"] へ書き換え、session option に include_external_packages = true を追加する（外部パッケージを forbidden_modules に置く契約はこの設定がないと拒否される）。既存 3 契約が同一段の区切りに使っている : は | へ直す（: は「非独立」＝相互 import 許可の意味であり、宣言している層独立性が検査されていなかった）。

[[tool.importlinter.contracts]]
name = "feature_extraction の層の依存方向（外側から内側のみ）"
type = "layers"
layers = [
    "feature_extraction.engine",
    "feature_extraction.boundary | feature_extraction.geometry",
    "feature_extraction.model",
]

[[tool.importlinter.contracts]]
name = "torch / timm / anomalib は boundary の外で import しない"
type = "forbidden"
source_modules = [
    "feature_extraction.model",
    "feature_extraction.geometry",
    "feature_extraction.engine",
]
forbidden_modules = ["torch", "timm", "anomalib"]

[[tool.importlinter.contracts]]
name = "geometry 内のモジュールは互いに独立（engine が合成）"
type = "independence"
modules = [
    "feature_extraction.geometry.tiling",
    "feature_extraction.geometry.patch_positions",
]

[[tool.importlinter.contracts]]
name = "model 内は ports → features → config／types・layout の一方向"
type = "layers"
layers = [
    "feature_extraction.model.ports",
    "feature_extraction.model.features",
    "feature_extraction.model.config",
    "feature_extraction.model.types | feature_extraction.model.layout",
]

[[tool.importlinter.contracts]]
name = "boundary 内は timm_backbone／anomalib_source → backbone_identity の一方向"
type = "layers"
layers = [
    "feature_extraction.boundary.timm_backbone | feature_extraction.boundary.anomalib_source",
    "feature_extraction.boundary.backbone_identity",
]

forbidden 契約が「重い依存を boundary に閉じる」という中心的な不変条件を検査する唯一の手段である（layers 契約は内部モジュール間の向きしか見ないため、geometry/tiling.py が torch を import しても検出できない）。間接 import も対象になる一方、まだ誰も import していない外部パッケージは検査対象から外れるだけなので実装途中でも CI は壊れない。layers 契約が列挙するモジュールは非 optional なので、5 契約の追加は全モジュール作成後に行う（Missing layer で失敗する）。

13. 再検証トリガー

次のいずれかを変えるときは設計の再確認が必要

  • PatchFeatureSet / ExtractorIdentity / ExtractionConditions のフィールド追加・削除・意味変更
  • positions の座標系（元画像座標・2 列 top, left）またはパッチ順序、および ExtractorIdentity.patch_stride の意味
  • InspectionImage の画素表現（(3, H, W) float32 [0, 1]）
  • 埋め込みの数値契約（float32・有限値・非ゼロノルム）
  • 依存方向、および boundary 外への torch / anomalib 型の露出
  • タイル端部の被覆規則（原点クランプ方式）— パッチ位置の重複分布が変わり下流のバンク構成に影響する
  • split 解決規則（VAL は生成せず TRAIN / TEST のみ、TEST は FROM_DIR 固定で正常テスト画像を必須）とマスク変換規則（gt_mask is None のみ未提供）
  • 再現性の保証範囲（同一デバイス・同一 tile_batch_size）
