patch-feature-store 設計サマリ

出典: .kiro/specs/patch-feature-store/design.md（1114 行）／新設パッケージ src/patch_feature_store。この HTML は要約であり、正典は design.md。

1. この spec の要旨

上流 ssl-vit-feature-extraction が作ったパッチ特徴を、後から検索できる索引として保持するパッケージ patch_feature_store を新設する。保持の単位はプロトタイプ（1 件以上のパッチ特徴を集約したもの）で、安定・再利用しない整数の識別子を持ち、正常性の担保根拠・種別・位置・ドメインタグ・由来キー・注釈メタと紐づく。

利用者は下流 spec の合成ルートである。primary-anomaly-detection は正常集合への近傍検索を、promptable-correction-layer は識別子を指定した類似度問い合わせを、evaluation-framework は由来キー単位の固定サイズバンクを使う。いずれも本パッケージの型と feature_extraction の型だけを介し、FAISS・anomalib・torch の型には触れない。既存 correction_layer・feature_extraction と同じ層パターン（model → 中間層 → engine）を踏襲する 3 つ目のパッケージになる。

この設計が引き受ける 6 つのこと

  • 初期構築と定期追加を同じ登録操作で受け付け、既存プロトタイプとの最近傍距離で「新規追加」か「集約」かを要求単位のバッチで決める。
  • 正常性の担保根拠が示された要求だけを受け入れ、根拠と種別を後から辿れる形で記録する。
  • 正常集合への近傍検索と、識別子指定の類似度問い合わせを、同じ距離尺度（コサイン）で提供する。
  • coreset 再選択と失効（expiry）間引きでサイズ上限を保ちつつ、間引き保護と kind=defect は除外対象から外す。
  • 永続化・再読込で同一クエリに同一結果を返し、抽出器同一性メタの不一致は登録時・検索時の双方で拒否する。
  • 由来キー単位の固定サイズバンクを複数構築し、同一指定の再実行で同一集合を再現する。

引き受けないこと

  • パッチ特徴の生成・タイル化・バックボーン切替（ssl-vit-feature-extraction）。
  • 異常スコア算出・ヒートマップ・ROI 候補抽出（primary-anomaly-detection）。
  • 正常性の検証そのもの、ROI 注釈受付、LLM による構造化（llm-feedback-structuring）。
  • 補正レコードの適用判定と match.prototype_ids の書き換え（promptable-correction-layer）。
  • 過検出率・AUROC などの指標算出（evaluation-framework）、バンクの版管理（Phase 5）、近似索引（IVF／PQ）の採用。

2. 層構成と依存方向

中間層を 2 つに分ける。catalog は台帳と純粋ロジック（受け入れ判定・集約・間引き・バンク）、boundary は外部依存（FAISS・anomalib・ファイル I/O・システム時刻）である。engine の PatchFeatureStore が両者を合成し、台帳とベクトル索引の同期を 1 箇所だけで担う。

3. 6 つの設計判断

① 索引は FAISS Flat（厳密解）に固定

近似索引（IVF／PQ）は採らない。再読込後の同一結果（要件 6.2）と、補正レイヤの match.similarity_threshold 判定はいずれも厳密解を前提にする。方式の切替は要件が求めておらず、採用は再検証トリガー扱いにする。

② 距離尺度はコサインに固定

保持するベクトルを L2 正規化し、内積をコサイン類似度として扱う。近傍検索は距離（1 − 類似度）、識別子指定の問い合わせは類似度を返す。後者が類似度なのは、補正レコードのしきい値が [-1, 1] の類似度で検証されているため。

③ 集約したら新しい id を発番する

集約後は重心が変わる。既存 id を続けると「同じ id が別のベクトルを指す」状態になり、補正レコードのしきい値判定の意味が黙って変わる。毎回新 id を発番し、集約前 id は retire して対応表に残す。

④ 集約判定は要求単位のバッチ最近傍

同一要求内のパッチ同士は「既存プロトタイプ」ではないので集約しない（次回登録か coreset 再選択で吸収する）。要求内の全クエリを 1 回のバッチ検索で処理する。逐次判定は実測で実運用に耐えない。

⑤ メタデータはプロトタイプ層と登録層に正規化

ドメインタグ・由来キー・担保根拠・注釈メタは登録要求単位の値なので、登録記録を権威にする。プロトタイプは寄与パッチごとに登録 ID と位置だけを持つ。この登録記録が要件 8 の操作記録そのものでもある。

⑥ バンクは主索引上の凍結された id 集合

バンクごとに索引を作らず、検索時に ID セレクタで絞る。構成は仕様（由来キー条件・サイズ・シード）から決定的に再現できるので、永続化の対象にしない。

4. 登録の流れ

入口は register ひとつで、初期構築と追加を区別する引数を持たない。違うのは担保根拠の種別（データセット由来か人手検証由来か）だけである。

受け入れ検査の順序

担保根拠と種別の整合 → 供給ラベルと申告種別の整合 → 抽出器同一性メタの全フィールド一致 → 埋め込み次元 → 数値契約（float32 化・有限値・非ゼロノルム）→ L2 正規化。空のストアへの最初の登録では、要求の同一性メタをストアの採用値にする。

種別受け入れる担保根拠供給ラベルの扱い
normalデータセット由来・人手検証由来の両方データセット由来なら image_label == NORMAL を要求（ANOMALOUS は拒否）
acceptable人手検証由来のみimage_label は見ない（ANOMALOUS のパッチを扱う経路）
defect人手検証由来のみ同上。正常集合検索からは常に外れる

DatasetEvidence の担保根拠はデータセットのラベルに由来するので、そのラベルが ANOMALOUS なら根拠は正常性を担保していない。この検査がないと欠陥パッチを kind=normal として登録できてしまい、要件 2 の目的（汚染の防止）が崩れる。判定は上流が供給した 2 つの値の突合に留め、正常性の検証そのものには踏み込まない。

集約すると値がどう決まるか

集約は「既存プロトタイプ 1 件 ＋ 同一要求内でそれを最近傍とした全パッチ」を 1 件へまとめる。判定は最近傍距離 <= しきい値（等号を含む）。

集約後の値規則理由
識別子新規発番。集約前 id は retire して対応表に載せる重心が変わった集約体に旧 id を使い回さない（判断 ③）
重心ベクトル寄与パッチ数で重み付けした平均を再正規化単位ベクトルの不変条件を保つ
寄与・ドメイン・由来キー和集合（寄与の併合）元の登録記録への参照を失わない
間引き保護 pinned論理和集約で保護を弱めない
失効期限 expires_atより遅い方（None は無期限＝最も遅い）集約で寿命を縮めない
種別 kind既存プロトタイプの種別を継ぐ候補は同一種別内からしか選ばない

同じ既存プロトタイプを最近傍とする複数のクエリは 1 件へまとめる。1 回の登録で同じ id が二重に retire されないようにするためである。

5. 検索対象の決め方

正常集合の検索では kind=defect を必ず外す。そのうえで domain（ドメイン限定）と bank_id（バンク限定）を独立に指定でき、両方指定されたら交差を対象にする。片方を優先して他方を無視することはしない。

ID セレクタの構築費用は対象件数に比例するため、包含 id が生存件数の半分を超える場合は補集合の除外セレクタへ自動的に切り替える。この判断は生存件数を知っている PrototypeRegistry が持つ。

6. 間引きの 4 分岐

サイズ上限を保つ手段は 2 つある。coreset 再選択（上限まで代表点を残す）と失効間引き（期限切れを外す）である。どちらも pinned は必ず残す。kind=defect は coreset では保護群に入るが、失効間引きの対象にはなる。

coreset 再選択の分かれ道は「選択件数 = 上限 − 保護群件数」で決まる。保護群は pinned または kind=defect のプロトタイプである。CoresetSelector.select の事前条件が 1 <= size <= 件数 なので、selector を呼べる区間は 1 つだけになる。

条件selector結果
選択件数が負（保護群 > 上限）呼ばないCoresetSizeLimitError(protected_count, size_limit)。何も除外しない（上限と保護を同時に満たす結果が存在しない）
選択件数 >= 選択可能群の件数呼ばない除外なしで終了。間引き記録も残さない（すでに上限以内）
選択件数 = 0 かつ選択可能群 >= 1 件（保護群 = 上限）呼ばない選択可能群を全件除外。「保護群だけを残す」で答えが一意に決まるので成功扱い
1 <= 選択件数 < 選択可能群の件数1 回だけ呼ぶ選ばれなかった id を検索対象から除外し、間引き記録を残す

除外された id はレコードを残したまま生存集合から外れる。対応表には載らないので、resolve は「間引きで除外」を意味する PrunedPrototype を返す。id は単調増加で払い出すため再割り当ては起こらない。

7. 途中で壊れない書き方

この設計には「壊れると黙って不整合になる」箇所が 2 つある。台帳とベクトル索引の同期と、6 ファイルにまたがる永続化である。どちらも 2 段階に分けて、失敗しても中間状態が残らないようにする。

状態変更は「準備 → コミット」

  • 状態を変える経路（register・reselect_coreset・prune_expired）は、まず検査・最近傍検索・集約計画・間引き対象の決定・識別子の確定までを行う。この段階では台帳もジャーナルも変えず、結果を RegistryChange に持つ。
  • コミットの順序は索引 → 台帳 → ジャーナル。台帳の反映（apply）と記録の追記は辞書とリストの更新だけで例外を出さないため、索引更新が失敗した時点で止めれば台帳は要求前のままになる。
  • register は add（新規 id と集約後 id）→ remove（集約前 id）の順に索引を更新する。add の失敗時は何も反映せず、remove の失敗時は直前の add を取り消してから送出する。間引きは remove だけなので取り消しは要らない。
  • 前提として単一スレッドの逐次利用に限る。並行呼び出しの排他は持たない。

永続化はディレクトリ単位で差し替える

6 ファイルを個別に os.replace すると、一部だけ新しい世代になる状態が起こりうる。そこで書き込みは次の順で行う。

  1. <store_dir>.staging/ に 6 ファイルすべてを出力する。
  2. 既存の <store_dir> を <store_dir>.previous/ へ改名する。
  3. staging を <store_dir> へ改名する。
  4. previous を削除する。

どの時点で中断しても、完全な世代が store_dir か previous のどちらかに残る。読み込み時は、store_dir が無く previous だけがあれば差し替えの中断と判断して戻してから読み、staging が残っていれば不完全な書き込みとして削除する。

読み込みでは pydantic（extra="forbid"）で各ファイルを検証したうえで、相互の整合も検査する。live_ids と行数の一致、生存 id の重複、生存 id のレコード存在、対応表の参照先の存在、生存集合と対応表の二重登録、同一性メタと埋め込み次元の一致など。違反は SnapshotIntegrityError(target, reason) で復元を中止する。

4 つのポート

class VectorIndex(Protocol):
    def add(self, prototype_ids, vectors: np.ndarray) -> None: ...
    def remove(self, prototype_ids) -> None: ...
    def search(self, queries, k, selection) -> tuple[tuple[NeighborHit, ...], ...]: ...
    def reconstruct(self, prototype_ids) -> np.ndarray: ...

class CoresetSelector(Protocol):
    def select(self, vectors: np.ndarray, size: int) -> tuple[int, ...]: ...

class SnapshotRepository(Protocol):
    def save(self, snapshot: StoreSnapshot) -> None: ...
    def load(self) -> StoreSnapshot: ...

class Clock(Protocol):
    def now(self) -> datetime: ...
  • 事前条件: add の vectors は (len(prototype_ids), 次元) の float32 単位ベクトル。search の queries も float32 単位ベクトルで k >= 1。select の size は 1 <= size <= len(vectors)。
  • 事後条件: search は入力クエリと同順・同数のタプルを返し、各要素は距離昇順で最大 k 件（対象が k 件未満なら全件）。
  • 不変条件: VectorIndex の id 集合は台帳の生存 id 集合と一致する。同期を行うのは PatchFeatureStore だけ。
  • 件数・次元を読む口はポートに置かない。次元の権威は採用済みの ExtractorIdentity.embedding_dim、件数の権威は台帳の生存 id 集合であり、同じ事実を 2 経路で公開しない。
  • CoresetSelector.select が返すのは id ではなく行インデックスである。実装が id 体系を知らずに済むようにするため、対応付けは PatchFeatureStore が持つ。

9. データモデル

集約ルートはプロトタイプで、ベクトルは索引側が持ち識別子で結ばれる。メタデータの権威は登録記録にあり、プロトタイプは寄与パッチごとに「登録 ID と位置」だけを持つ。プロトタイプ 100 万件規模でメタを複製すると重複が支配的になるためである。

識別子がとる 3 つの状態

4 つの不変条件

  1. 識別子は単調増加で払い出され、再利用されない。
  2. 1 つの識別子は「生存」「集約により retire」「間引きにより除外」のいずれか 1 つの状態を持つ。
  3. 生存識別子の集合はベクトル索引の識別子集合と一致する。
  4. プロトタイプの寄与パッチは 1 件以上であり、その件数が集約時の重みとバンクのパッチ数になる。

2 つの権威

型持つもの役割
PrototypeRecord（非公開）prototype_id, kind, pinned, expires_at, contributionsプロトタイプ単位の権威。間引き判定の入力はこの 4 項目とベクトルだけ（補正レコードは見ない）
RegistrationRecord（公開）registration_id, occurred_at, image_id, split, domain, provenance, evidence, 注釈メタ, structured_json_ref, 適用メタ, prototype_ids登録単位の権威。同時に要件 8 の操作記録そのもの。追記のみで、後の集約・間引きでは書き換えない

RegistrationRecord.prototype_ids は「登録時点で生成された id」であって現在の構成ではない。現在の状態を知るには resolve か describe を使う。

絞り込み条件は 2 型に統合する

ドメイン限定（要件 3.6）、メタデータ絞り込み（4.4）、バンクの包含・除外（7.1、7.2）は、いずれも「軸ごとの値集合による一致判定」である。そこで DomainCriteria（工程・材料・装置）と ProvenanceCriteria（ウェハ ID・ロット ID・撮像日）の 2 型に統合し、上流の DomainTags / ProvenanceKeys と軸を 1 対 1 に対応させる。

  • 空集合の軸は「無指定」で何にでも一致する。値が None のタグは、その軸が無指定のときだけ一致する。
  • BankSpec.exclude = None は「除外判定そのものを行わない」。全軸が空集合の ProvenanceCriteria は「何にでも一致」なので、これを除外条件に使うと全候補が外れてしまい「除外なし」を表現できない。

検索・照会の戻り値

10. 永続化レイアウト

<store_dir>/
├── extractor_identity.json   抽出器同一性メタ。空ストアでは null
├── prototypes.jsonl          1 行 1 プロトタイプ。発番済み全 id のレコード
├── live_ids.npy              int64 (M,)。vectors.npy の行に対応する生存 id
├── vectors.npy               float32 (M, D)。L2 正規化済み
├── merged_into.json          集約前 id → 集約後 id の対応表
└── journal.jsonl             1 行 1 操作記録（登録記録と間引き記録）

<store_dir>.staging/ と <store_dir>.previous/ は差し替えの途中だけ存在する作業ディレクトリで、正常終了後は残らない（7 章）。

「持たないもの」にも理由がある。

  • 除外状態の専用フィールドを持たない。prototypes.jsonl にあって live_ids.npy にも merged_into.json にも現れない id が「間引きで除外済み」である。
  • 次の識別子を保存しない。発番済み id のレコードは削除しないので、最大値 + 1 で復元できる。
  • バンクを保存しない。仕様とストア状態から決定的に再構築できる（要件 7.4）ため、権威を二重に持たない。
  • スキーマ版フィールドを持たない。版管理は Phase 5 の対象で、本 spec でのレイアウト変更は再検証トリガーとして扱う。

Flat 索引は保存した float32 ベクトルから決定的に再構築されるので、再読込後も同一クエリに同一結果を返す（要件 6.2）。

既存の correction_layer/boundary/prototype_store.py は同じ問題（プロトタイプ id と埋め込みの kNN）を扱うが、不変の索引を作る読み取り専用の実装であり、増分追加・間引き・メタデータ層・永続化を持たない。本 spec はそれを置き換えず、correction_layer を一切変更しない。補正レイヤが注入する SimilaritySource の実装候補が将来増える、という関係にある（similarities は同じ意味のコサイン類似度を返す）。

12. 要件との対応

要件基準主要な実現手段
1. パッチ特徴の登録と増分追加8入口は register ひとつ。バッチ最近傍としきい値で新規／集約に振り分け、RegistrationOutcome.prototype_ids を入力パッチ行と同順で返す。次元不一致は EmbeddingDimensionMismatchError
2. 正常性が担保されたデータだけを登録するガード7evidence を必須フィールドにし、種別との整合と供給ラベルとの整合を admission が検査。kind=defect は正常集合検索から常に外す
3. 近傍検索とドメイン限定8search_normal がコサイン距離で最大 k 件。-1 パディングを除去するので k 未満なら全件。domain と bank_id は交差（5 章）
4. メタデータの保持と絞り込み6登録記録を権威にし、describe が寄与ごとに登録記録付きのビューを返す。find_prototypes は条件一致の生存 id を返す。未提供は None か空マップのまま補完しない
5. coreset 再選択と expiry 間引き7保護群（pinned または defect）を残して 4 分岐で処理（6 章）。除外 id はレコードを残したまま生存集合から外れ、resolve が PrunedPrototype を返す
6. 永続化・再読込と抽出器同一性の互換判定6ディレクトリ差し替えで保存し、pydantic 検証＋相互整合検査で読む。同一性メタは全フィールド比較し、不一致は登録時・検索時の双方で ExtractorIdentityMismatchError
7. 評価用の固定サイズバンクの複数構築7候補 id を昇順に並べ numpy.random.default_rng(seed) で非復元抽出。defect は候補に入れない。不足は BankSizeUnavailableError でバンクを作らない
8. 登録・間引き操作の記録4OperationJournal が登録記録と間引き記録を追記し、operations(since, until) が実施日時の昇順で返す。率の算出は境界外

design.md のトレーサビリティ表は 1.1 から 8.4 まで欠番がない。境界外に置いた関心事（スコア算出・remap・指標算出・Phase 5 の版管理）はどの受入基準にも吸収していない。

13. エラーの分類

要件が「登録せず報告する」「検索を実行せず報告する」と定める経路は、すべて型付き例外で報告する。検査は状態変更の前に終わらせるので、例外が出たときに台帳と索引は変わらない。すべて PatchFeatureStoreError を継承し、呼び出し側がパッケージ単位で捕捉できる。

例外送出条件保持する情報
EmbeddingDimensionMismatchError登録済みの埋め込み次元と要求の次元が違うexpected_dim, actual_dim
NormalityEvidenceRequiredError担保根拠が欠ける／種別と整合しない／データセット由来の根拠に対して供給ラベルが ANOMALOUSkind, reason
ExtractorIdentityMismatchError抽出器同一性メタが一致しない（登録時・検索時の双方）mismatches（IdentityMismatch(field, expected, actual) の列。不一致項目をすべて含める）
SnapshotIntegrityError読み取り失敗・スキーマ違反・相互不整合target（対象ファイルまたは検査項目）, reason
CoresetSizeLimitError保護群件数が上限を超える（等しい場合は成功経路なので送出しない）protected_count, size_limit
BankSizeUnavailableError候補が size に満たない（バンクは作らない）bank_id, requested_size, available_count
UnknownBankError未構築のバンクを検索・照会で指定したbank_id
ValueError数値契約違反（非有限値・ゼロノルム・形状不一致）は admission、k < 1 は NormalSearchQuery の構築時—（上流契約で保証されるべき入力の逸脱。既存 PrototypeStore の扱いに揃える）

観測の一次手段は操作記録である。登録・間引きの実施日時と対象識別子が残るので、下流の evaluation-framework が追加前後の流出率・過検出率の変化を突き合わせられる。本パッケージ自身はログ出力を持たない。

14. import-linter 契約

pyproject.toml の root_packages に patch_feature_store を加え、7 つの契約で依存方向を CI 検査する。src/ の既存パッケージ・docs/・.kiro/steering/ は変更しない。

#種別内容守るもの
1layersengine > boundary | catalog > model層の逆流と catalog ⇄ boundary の相互 import の禁止
2independencecatalog の 6 モジュール台帳同士を結合させず、配線を engine に集める
3layersmodel の 11 モジュールを 7 段に並べる（ports → snapshot → prototype → registration | operations | bank → query → errors → criteria | config | types）型定義の循環の防止
4forbiddenmodel・catalog・engine から faiss・torch・anomalib重い外部依存を boundary に閉じる（中心的な不変条件）
5layerssnapshot_store | faiss_index | anomalib_coreset | clock > snapshot_schemaアダプタ同士の相互 import の禁止（永続化アダプタが FAISS に触らない）
6forbiddencorrection_layer・feature_extraction から patch_feature_storeパッケージ間の依存方向を一方向に固定
7forbiddenpatch_feature_store から correction_layer契約 6 の逆向き。両方揃って初めて「correction_layer と相互依存しない」が検査される（feature_extraction への依存は許可）

同一層を区切る | は import-linter の independent 指定であり、同一層のモジュール同士の import も禁止される。したがって依存があるモジュールは層順で解く必要がある（例: PrototypeContributionView が RegistrationRecord を持つので model.prototype は model.operations の上位）。また layers 契約は列挙したモジュールが存在しないと Missing layer で失敗するため、契約の追加は全モジュール作成後に行う。

16. 性能とスケール

実測（faiss-cpu 1.14.3、WSL2 CPU、D=384）: 50 万件への add が 0.38 秒、1024 クエリ・k=1 のバッチ検索が 8.27 秒（1 クエリ約 8 ミリ秒）。除外セレクタ付きは 7.87 秒、生存の半数を包含するセレクタ付きは 5.97 秒。

1 画像の全パッチ登録は成立しない

  • 登録費用は O(登録パッチ数 × 生存件数 × 次元)。8000 × 8000 画像 1 枚（タイル 512・ストライド 16 で約 26 万パッチ）をそのまま登録すると約 35 分かかる。
  • したがって呼び出し側が登録対象を絞るか、coreset 再選択で上限を保つ必要がある。上限値そのものは運用（evaluation-framework のストア規模スイープ）で決める。
  • メモリは生存件数 × 次元 × 4 バイト（50 万件・384 次元で 0.77 GB）に、寄与とレコードの Python オブジェクトが加わる。DGX Spark の 128 GB 統一メモリを前提とする。
  • coreset 選択は候補ベクトル全体を取り出して torch テンソルへ移すため、選択時に索引と同規模の一時メモリを要する。
  • find_prototypes とドメイン限定検索は、登録記録の絞り込み（登録件数に比例）とプロトタイプ走査（生存件数に比例）を伴う。1 クエリの近傍探索より重くなる場合があるため、ドメイン限定は任意指定に留める（既定は単一プール）。

17. 再検証トリガー

次のいずれかを変えるときは設計の再確認が必要

  • PrototypeRecord / RegistrationRecord / NeighborHit / SimilarityLookup / BankComposition のフィールド追加・削除・意味変更
  • 距離尺度の変更（コサイン距離 = 1 − 類似度、内部表現は L2 正規化済みベクトル）— 補正レイヤの match.similarity_threshold の解釈に直結する
  • 集約時に新識別子を発番する方針（既存識別子を継続しない）の変更 — 補正レイヤの remap 追従の前提が変わる
  • 索引方式を Flat から近似索引（IVF／PQ）へ変更すること — 厳密解でなくなり要件 3.1／6.2 の前提が変わる
  • 永続化ディレクトリのファイル構成・ファイル名・レコード形式の変更
  • 間引き規則（保護対象、上限の充足可能性判定）の変更
  • バンクを永続化対象に含める変更（現設計はプロセス内の派生物として扱う）
  • 上流 feature_extraction の ExtractorIdentity へのフィールド追加 — 互換判定の比較対象が変わる
  • 注釈メタ・適用メタのスキーマ確定（現在は不透明な文字列マップとして素通ししている）
